# Which ANBERNIC Android handheld can use my library?

**Use CouchCHD on the host; play the copy on the handheld.** Send already-compressed games over home Wi-Fi with [CouchCHD Receive](../README.md#anbernic-rg405m--android--daijishō), or copy to a mounted portable card without installing an app. Neither path requires root, flashing firmware, or replacing the card layout.

The RG405M is a **documented target to try**, not a physical-device certification. The [release pipeline](../.github/workflows/release.yml) packages Linux and the Android receiver; [export tests](../tests/test_handheld.py) check file handling, not emulator playback. Use [the profile/player list in your build](../README.md#choose-a-handheld-by-firmware-and-player) to see what it can export.

## Identify the device **and the OS running now**

Read the suffix on the case, then open **Settings → About** on the handheld. These are manufacturer specifications, not minimum requirements or installed-player inventories. RAM/internal storage are in GB, not the optional bundled game-card capacity.

## Choose by installed player, not by chip

A game needs three things: the frontend must **list** its extension, the named player must **decode** this type of image, and **this title** must actually play on this hardware. Confirm the emulator's version/package and the core's build in their About/Information screens. Daijishō's [player and extension table](https://github.com/TapiocaFox/Daijishou/wiki/Players-and-File-Extensions) describes launch configurations, not proof of any of those three. In particular it distinguishes standalone apps from `-lr` (RetroArch cores), and warns about the Play Store RetroArch builds with its players.

## Reuse a mixed library without breaking the existing one

1. **Look before converting.** In **NAS / Cloud**, refresh the named library on the host: a read-only NTFS collection on Bazzite, a Deck/EmuDeck library, a mounted NAS or a configured remote. Pull a selected compatible output into a separate writable library. A last-seen inventory is not an online game server, and matching names aren't matching disc revisions. If there's only a supported loose/ZIP source, convert a copy on the host with **Keep originals**. See [library, ZIP and export workflows](../README.md).
2. **Use the right card and directory.** Inspect the existing games volume in a reader. Example: if games already live under `ROMs/PSX` and `ROMs/DC`, target those actual platform directories, preserving capitalization and relatives. Those names are examples, not a universal GammaOS, stock or Daijishō convention. Never point the exporter at the OS/boot partition, a BIOS or saves folder, or the only master dump. On shared dual-boot media, let each OS index the same game folders only if both can read the filesystem and the selected formats. Keep per-OS emulator settings and saves separate.
3. **Choose the transfer the storage supports.** A directly mounted **portable** card allows the host exporter to compare the copied bytes, skip identical files and refuse conflicts. Android [adopted/private storage](https://source.android.com/docs/core/storage/adoptable) is encrypted to its owning device; do not reformat it to mount it on a PC. For internal/adopted storage or USB [File transfer](https://support.google.com/android/answer/9064445), export to a separate host staging directory, then copy the complete pack with your file manager. MTP is not a POSIX mount or a CouchCHD-verified last hop. Preserve hidden member directories too; compare a readback from the card/device with the staging copy if you need byte-level evidence.
4. **Point the frontend and player at the same copy.** In [Daijishō](https://github.com/TapiocaFox/Daijishou/wiki/How-to-Use-Daijish%C5%8D), import the platform if missing, then highlight it → **Add more → Select folder → Sync**. Under **Edit platform → Default Player**, select the installed emulator/core and save; individual games can override this. On a stock RG Home device use its existing player/library or launch directly inside the emulator; don't apply Daijishō button instructions to a different app.
5. **Keep grants narrow.** Use the Android picker for the actual platform subfolder, e.g. `ROMs/PSX`, not the whole SD root or `/Android/data`. With [Android's Storage Access Framework](https://developer.android.com/training/data-storage/shared/documents-files#grant-access-directory), a tree grant belongs to the requesting app. A launcher may forward a single-file URI; that's not a permanent grant for a separate emulator to open all playlist members. Grant the player its own game folder if requested. Android 11+ restricts selection of internal/reliable SD roots, `Download`, `Android/data` and `Android/obb`. Re-select the folder if the card or grant changes. Don't transplant absolute `/storage/<id>` paths from a different device.

**If it doesn't launch:** If the player opens the game directly but the launcher doesn't list it, check the selected directory, active player's filename filter and Sync. If it lists the game but won't launch it, check the player package, installed core, BIOS and [URI vs file-path handling](https://github.com/TapiocaFox/Daijishou/wiki/Frequently-Asked-Questions#player-not-launching). If the standalone player fails too, changing the launcher's regex won't help. For a failed disc swap, check member paths, capitalization and folder access before changing codecs. For a missing save, check the existing memory-card name or memstick directory before starting a new game.

## Physical-fleet acceptance: what would count as a pass?

Use an owned dump or redistributable fixture, a spare **game** card or a backed-up game folder, and a second copy of the game's existing save. Leave system cards and firmware alone. Test at least one actual representative per distinct OS/player pairing; don't transfer a pass between siblings. Start with RG405M, a low-memory RK3566 or RG552 already on Android, a T820, then a newer Android device. A Linux-only stock sibling is a useful negative control: no Android-only instructions should be required.

| Check | Record on the real device |
|---|---|
| Identify and stage | Model **and suffix**, booted firmware/build, frontend, emulator package/version + core revision, card/slot, portable vs internal, transport, actual relative game folder, title/region/disc hash, format/codec, host build. Record direct-card hash check or explicitly mark “MTP last hop unchecked.” No BIOS, saves or ROM uploads needed. |
| Controller entry and cancel | On the host, navigate export, choose the matching profile/player, select one game, review the destination and back out once without writing. Complete the transfer. On the handheld, use D-pad, confirm/back and shoulder buttons from frontend to launch, in-game menu, and back to the same library item. Note any Android permission dialog requiring touch, six-button ARC mappings, or the wrong screen receiving focus on a dual-screen unit. |
| Discover, then play | Sync or rescan. Confirm the **intended** revision is listed once and opens via the configured player **and** directly inside it. Record “listed,” “booted” and “played” separately. Try a repeatable gameplay segment with audio/input; record duration, native resolution, renderer/settings and any slowdown, not just a boot screenshot. |
| Playlist and save | Use a real two-disc test when claiming M3U: copy playlist plus members; launch its entry, open the emulator's [disc control](https://docs.libretro.com/guides/disc-swapping/), eject/change/insert at a known transition and continue. Load an existing **in-game save** from the backed-up test profile, save into a new slot, quit fully, then reload. A save state alone doesn't count. [Beetle PSX's card naming](https://docs.libretro.com/library/beetle_psx_hw/#saves) can change when switching disc → playlist; [Flycast VMUs](https://docs.libretro.com/library/flycast/#directories) and [PPSSPP's Memory Stick folder](https://www.ppsspp.org/docs/getting-started/save-data-and-storage/) are separate from the game files. Never overwrite a live card/save to make a test pass. |
| Persistence and conflicts | Safely eject/remount or reboot, rescan and repeat launch/load. For an already dual-booted device repeat in the other OS only if claiming a shared library. Re-export the same test: identical bytes should be skipped. On **disposable copies only**, a different file at the destination name must be reported as a conflict, not overwritten. |

Label the result **documented** (upstream says the format is accepted), **reported** (an owner observed a specific action), or **physically checked** (identified unit/build/title with the results above, including failures or “not applicable”). A “copied” pass is not a “played” pass, and no single game certifies an entire emulator or family.

## Why isn't the Linux ARM download an APK?

The [CouchCHD release workflow](../.github/workflows/release.yml) targets Debian/glibc userspace. Android uses its own [NDK ABIs](https://developer.android.com/ndk/guides/abis); an ARM64 CPU is not an Android distribution format. Daijishō's **Apps** tab or [pin-apps widget](https://github.com/TapiocaFox/Daijishou/releases/tag/v1.3.0) can open an installed app, not an AppImage, tarball or shell script as a player. Don't run the Linux installer on Android.

CouchCHD Receive is a [signed Android app](https://developer.android.com/studio/publish/app-signing) for local transfers only. A native on-device converter would separately need Android-native codec code, space for staging/verification, and device testing. Do not download a Linux converter to the card and try to run it as an Android app.
